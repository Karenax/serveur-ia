# Audit UX d’Agent — 22 octobre 2026

Ce rapport décrit l’état **avant correction**. Les corrections demandées ensuite
sont consignées dans [59_UX_CORRECTIONS_20261022.md](59_UX_CORRECTIONS_20261022.md),

## Conclusion

Agent dispose d’une base métier solide : navigation par grandes rubriques, contexte projet explicite, séparation entre propositions et décisions humaines, accès aux sources et conservation des notes. Les difficultés principales concernent la protection des actions sensibles, la continuité d’accès en cas de panne et la cohérence des parcours entre modules.

**20 constats : 1 P0 de prévention, 3 P1, 13 P2 et 3 P3.** Le P0 concerne un risque de suppression dans Agent ; aucune perte de données n’a été provoquée ou observée pendant l’audit. Les priorités ci-dessous sont une appréciation experte, pas une mesure issue de tests utilisateurs.

L’objectif recommandé est de rendre les parcours existants plus sûrs et plus directs. Conserver les modules CDC, BE, Revues, Atelier, Import Sage, leurs données et les validations humaines.

- Audit visuel avec **Playwright MCP / Edge**, sur le bundle existant de `web/dist`, sans reconstruction. Assets observés : `index-B8blibkx.js` et `index-aq9M5uKt.css`.
- Instance temporaire sur **127.0.0.1:8011**, avec copies SQLite cohérentes de Brain et ERP, stockage d’audit distinct, `lifespan=off`, sans démarrage des workers. Les requêtes autres que GET/HEAD/OPTIONS sont bloquées par un middleware. Le service normal reste sur 8001 ; XPilot 8000 n’est pas sollicité.
- Pour vérifier le lecteur MIME, 92 originaux EML récents ont été copiés dans le stockage privé d’audit. L’affichage texte observé avant cette copie est exclu des défauts : c’était une limite de la fixture, pas une régression démontrée du lecteur.
- Résolutions : **1440 × 900**, **1280 × 720** pour Studio/CDC, **390 × 844** pour les rubriques principales et certains parcours détaillés. Thèmes clair et sombre examinés sur Informations et Mails.
- Contrôles : lecture des écrans, navigation et sous-vues, noms accessibles des champs, Tab/Échap, menu mobile, recherche, consultation d’une preuve, états vides et panne réseau simulée.
- `npm --prefix web run ux:check` : **119 fichiers, 77 avertissements**, commande réussie. Ces avertissements sont des pistes ; ils ne correspondent pas à 77 défauts établis.
- Référentiel complémentaire : [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md), récupéré pendant l’audit ; conventions du dépôt et `docs/24_UI_UX_REDESIGN.md`.

## Constats prioritaires

### UX01 — P0 : purge d’un mail sans confirmation dans certains parcours

**Écran :** Mails, Options du mail ; dépôt sur la destination « Écarter ».

Le bouton « Écarter ce mail d’Agent » envoie directement la demande de purge. Le dépôt vers « Écarter » appelle également la purge. Le choix de la vignette suivi du bouton principal présente mieux la conséquence, mais ne protège pas les autres chemins.

**Preuve :** `20-mail-discard-before.png` ; interaction interceptée : **1 requête de suppression, 0 dialogue de confirmation, aucune suppression exécutée**. Code : `web/src/components/MailWorkspace.tsx:248`, `:306`, `:492` ; effet réel dans `app/services/mail_discard.py:20`.

**Impact :** un geste mal interprété peut purger le contenu d’Agent et les connaissances exclusivement associées. Le service prévoit une sauvegarde technique et préserve l’original externe ; cela ne fournit pas une annulation immédiate dans l’interface.

**Correction proposée :** confirmation commune à tous les chemins, avec nombre de mails et conséquence exacte ; distinguer « Mettre dans Divers » de « Supprimer le contenu d’Agent ». Présenter la procédure de récupération, et envisager une annulation si techniquement compatible. Conserver les sauvegardes existantes.

### UX02 — P1 : la panne du portefeuille bloque l’accès à toutes les rubriques au démarrage

**Preuve simulée :** réponse 503 uniquement sur `/api/v1/portfolio`, capture `error-portfolio-simulated.png`. La navigation disparaît ; il reste le message d’erreur et « Réessayer ». Après retrait de la simulation, ce bouton rétablit bien l’application. Code : `web/src/App.tsx:114`.

**Impact :** l’utilisateur ne peut pas rejoindre Mails ou Sources depuis ce démarrage, même si leurs services seraient disponibles.

**Correction proposée :** rendre la coquille de navigation indépendamment du chargement du portefeuille ; limiter le blocage aux fonctions qui nécessitent cette liste. Conserver « Réessayer » et la distinction entre absence de données et panne.

### UX03 — P1 : plusieurs champs métier n’ont pas de nom accessible associé

**Preuves visuelles et DOM :** `19-nouveau-projet-manuel.png`, `18-nouveau-projet.png`, `sub-1.png`, `atelier-Pointage.png`, `atelier-Nomenclature.png`.

Exemples confirmés : Code/Titre du nouveau projet, chemin réseau, Titre/Citation/Page d’une exigence, Personne/Motif du pointage, Référence/Désignation de nomenclature. Le placeholder ne remplace pas un libellé associé et disparaît à la saisie.

**Code :** `web/src/App.tsx:432`, `:1556`, `:1563` ; `web/src/components/WorkshopPanels.tsx:59`, `:62`, `:112`.

**Correction proposée :** libellés visibles courts associés aux champs ; nom explicite pour la page et les quantités ; instruction d’erreur près du champ. Vérifier le parcours au lecteur d’écran lors de la correction. Les 77 alertes heuristiques doivent rester soumises à une revue contextuelle.

### UX04 — P1 : la preuve d’une information n’est pas directement accessible depuis la vue projet

**Preuves :** `06-knowledge-1440.png`, `16-projet-connaissance-1440.png`, `source-inspector.png`. La vue globale propose la source et son inspecteur. La table Informations du projet affiche Type/Sujet/Valeur/Statut/Écarter, sans action directe vers la preuve de chaque ligne. Code : `web/src/App.tsx:1276`, comparaison avec `web/src/components/WorkspaceViews.tsx:453`.

**Impact :** le chargé d’affaire doit quitter son contexte pour contrôler une information avant de l’utiliser. La mention « Issue d’une source » ne permet pas, à elle seule, de vérifier cette source.

**Correction proposée :** réutiliser l’inspecteur de preuve dans la table projet ; rendre visibles date, provenance et mode de validation à la demande, sans dupliquer le contenu.

## Contrôles favorables

- Grandes rubriques et modules métier conservés ; codes et titres de projet visibles dans l’espace projet.
- Menu mobile fermé : barre hors écran et `inert` ; ouverture déplace le focus dans la navigation, Échap le rend au bouton d’ouverture. Le chevauchement mobile évoqué dans le contrôle d’installation précédent n’est **pas reproduit après stabilisation** dans cet audit.
- Focus clavier visible : contour de 3 px observé sur la recherche. Lien « Aller au contenu » présent.
- Inspecteur de source : modale nommée, focus à l’ouverture et fermeture par Échap vérifiés.
- Recherche sans résultat : message explicite proposant d’autres mots ou un périmètre plus large.
- Panne simulée : message d’erreur compréhensible et récupération par « Réessayer » réussie.
- Lecteur mail : HTML MIME retrouvé avec les EML copiés ; images externes désactivées initialement et action d’affichage explicite. Thème sombre de l’application conservé autour du document d’origine clair.
- Informations globales : source, mode « Retenue par défaut » et action de déclassement identifiables ; vues Déclassées et À vérifier disponibles.
- Préparation des réunions : distinction utile entre moteur installé, chargé, essai et qualification. Les réserves sur la transcription sont nécessaires ; les regrouper ne doit pas les effacer.
- Échantillon automatisé de contraste : aucun ratio inférieur à 4,5 trouvé sur les boutons, liens, labels et badges visibles et activés du portefeuille clair testé. Ce contrôle exclut les autres écrans, placeholders, images, états désactivés et effets complexes ; **aucune conformité globale de contraste n’est annoncée**.
- Pas de débordement horizontal de la page entière observé à 390 px sur les rubriques visitées ; les tables et certaines listes peuvent défiler intérieurement.

## Plan de correction proposé

1. **Sécuriser** : UX01, puis UX02 ; tester tous les chemins de purge avec données fictives et simuler séparément la panne du portefeuille.
2. **Rendre les décisions vérifiables** : UX03, UX04, UX09 et UX15 ; labels, preuves et statut commun des informations.
3. **Raccourcir les parcours quotidiens** : UX05, UX07, UX08, UX10, UX11 et UX16 ; commencer par classer un mail, contrôler une exigence et reprendre un compte rendu.
4. **Stabiliser la présentation** : UX06, UX12, UX13, UX14 et UX17 ; garder la navigation et toutes les fonctions métier.
5. **Finir et vérifier** : UX18–UX20, clavier, lecteur d’écran, zoom 200 %, thèmes, ordinateur portable et mobile. Rejouer le contrôle UX et les tests pertinents après les corrections effectivement demandées.

Pour vérifier le gain, mesurer avec un utilisateur représentatif : retrouver une source depuis une information du projet ; traiter une exigence ; retrouver le bon compte rendu ; classer un mail incertain ; récupérer après une erreur. Relever réussite, hésitations, retours en arrière et compréhension de l’action, avant/après correction.

## Limites et conservation

Aucune interface produit, donnée métier active, configuration IA ou bundle servi n’a été modifié par cet audit. Aucune publication, transcription, capture microphone, génération ou synchronisation n’a été déclenchée. Les seules écritures applicatives tentées pendant les vérifications ont été refusées/interceptées dans la copie isolée ; les préférences de thème du navigateur d’audit ont été rétablies sur Clair.

L’audit ne qualifie pas les performances du serveur normal, l’index EG2 actif, la qualité de transcription, l’audio conservé ni les réponses IA. Le fichier audio de la séance n’a pas été copié : son erreur de lecture 409 dans la fixture est exclue des défauts. Les compteurs nuls d’indexation dans la copie ne prouvent rien sur l’index de production. Les erreurs dues aux écritures bloquées de la fixture ne sont pas des défauts de production.

Le formulaire Nouvelle séance a d’abord été refusé par le contrôle automatique d’actions. Après lecture de `WorkspaceViews.tsx:275` montrant que l’ouverture ne modifie que l’état React, son affichage seul a été vérifié, sans soumission. Aucune création de séance n’a eu lieu.

Pas de test utilisateur, lecteur d’écran réel, zoom navigateur 200 %, habilitation lecteur, capture matérielle ou cycle complet de modification/annulation. Pas de certification WCAG. Les suites Python/Ruff/build ne sont pas relancées : aucun code produit n’a changé ; leur réussite n’est pas déduite du contrôle UX. Aucun commit ni push.

Les captures transitoires `mobile-mail-390.png`, `mobile-meetings-390.png`, `studio-cr-390.png`, `settings-3.png` et `extra-0.png` ne doivent pas servir seules à conclure sur un écran chargé. Utiliser leurs versions stabilisées lorsqu’elles existent. Les captures privées, copies SQLite et originaux EML de la fixture sont conservés localement ; aucune suppression de données n’est incluse dans la mission.
